# 《河湾议会》Three.js 最小 Demo 设计

## 1. 实验目标

**同一块布，玩家能否用一句话把它变成一户人的住处，也能把它用来保住一堆木料？** 两种做法都要占用场景里真实存在的篷布，都要在画面上看出区别，并在夜间产生不同结果。

这是一个约三分钟的单屏实验。玩家看场景、提办法、决定是否启用，再让一户人实际动手。首版只接入“游戏经理”模型，张家和李家的行动由玩家操作。待这条链路成立后，再让利益方 NPC 自行提案或拒绝合作。

## 2. 玩家能看到和使用什么

洪水刚退，今晚还会下雨。界面提问：**“只有一间仓房，两户人家和一堆木料今晚怎么安排？”** 开局不展示搭棚或盖货的示范答案。

| 场景要素 | 开局状态与可用属性 |
| --- | --- |
| 张家、李家 | 都在仓外，都能搬运、展开和固定篷布。每户有一次白天劳作机会，入夜选择落脚处。 |
| 仓房、干地 | 仓内原有一个住宿位。外墙旁有一户大小的平整干地，留有进入通道。墙上有高位挂点，地边有现成的低位系环。 |
| 篷布 | 一块带系绳的防雨布，起初折在货堆一角。展开尺寸足以覆盖干地上的一户，或覆盖整堆木料。折叠状态只遮住货堆一角。 |
| 木料 | 夜雨前存放在仓外，占据固定空间；顶部可承托篷布。入夜时整堆受到覆盖即可保持干燥，否则记为受潮。 |

一台固定斜俯视相机要同时看清仓门、干地和货堆。点击物件即可查看材质、尺寸、归属及当前占用情况；同一份场景事实也提供给模型。玩家看到“有一块布”，就应当能一直追踪这块布去了哪里。

## 3. 两局对照试玩

每局从同一份初始场景重开。下表是开发验收脚本；试玩者可用自己的措辞，模型应保留其提出的条件。

| 步骤 | A 局：给张家搭棚 | B 局：把木料盖好 |
| --- | --- | --- |
| 玩家提出办法 | “没出过工的人家，白天可以把布系在仓边搭棚，晚上自己住。” | “让张家把这块布展开盖到木料上，今晚别让木料淋湿。” |
| 预览 | 半透明轮廓显示布将从高挂点斜拉至地边系环；界面列出占用的干地、篷布和一次劳作。 | 轮廓贴住货堆顶部并垂到边缘；列出同一块布和一次劳作。 |
| 执行 | 玩家启用规则，再让张家动手。货堆角落的折布消失，同一块布在墙边展开。点击棚面可以查看谁搭建、谁能入住。 | 张家动手后，布覆盖木料，干地仍为空地。点击布面可以查看它正在保护哪堆货。 |
| 夜间结算 | 张家选择棚下，李家选择仓内。两户都有住处，木料受潮。 | 木料干燥，仓内仍只有一个位置。玩家选一户入仓，另一户在本次安排下露宿。 |

启用规则仅让对应行动可选。若双方都没有动手就入夜，折布仍在原位，仓外没有住处，货堆也得不到完整遮盖。这是排查“模型一说，结果就发生”的基线。

## 4. 实现分工：规则、场景和账本共用一份事实

| 组件 | 输入与职责 | 输出 |
| --- | --- | --- |
| 游戏经理模型 | 读取玩家原话、场景对象及其可用属性，将办法表达成有执行者、条件和操作的草案。对关键歧义可以追问。 | 声明式行动草案，例如“尚未出工的一户可在白天展开指定布面，将四角固定到指定挂点”。 |
| 规则引擎 | 解析对象引用，校验权限、阶段、行动余量、材料尺寸、支撑与空间占用；预览后在实际执行时重新校验。 | 成功时一次性提交新的世界状态。失败时列出具体缺口，时间、资源和画面保持执行前状态。 |
| Three.js 场景层 | 从世界状态取得物件标识、支撑点和表面形状，在浏览器运行时生成或更新网格，并把点选结果映射回物件。 | 可见的篷布、干地与货堆；供玩家检查、操作的实体。 |

**只维护一份已生效的搭建记录。** 例如张家搭好棚后，记录所用篷布、实际固定点、布面顶点、占用地块、搭建者与有效时段。游戏经理只需引用场景中的挂点、货堆和材料，无须猜测世界坐标。引擎根据这些引用和布的尺寸确定最终形状。Three.js 读取这组顶点绘制布面，夜间结算读取相同的覆盖范围、支撑关系和空间高度。修改展示名称或隐藏日志，都不会改变结果。

**画得出来的物体，还要算得出用途。** 首版可把干地和货堆顶面分别简化成矩形。防雨布的投影完全盖住货堆顶部，才判整堆受保护；要容纳一户，还要在可步入的干地上覆盖一户大小的连续区域，并达到关卡规定的最小净高。验收地图的尺寸与挂点高度应能满足 A 局条件。布贴在木料上时，下方空间已被货物占据，自然不会产生住宿位。谁有入住资格，再按当局生效的制度判断。

## 5. 给模型的最小操作能力

开发者提供通用操作，包括查询对象与属性、检查条件、移动或展开材料、建立支撑或固定关系、占用或释放资源，以及登记或转移使用权。模型可以为一组操作声明新的行动名称、适用条件和交互入口。具体结果须从可用材料和空间推导；草案不能仅凭“这是一顶帐篷”就给账本增加床位。

Three.js 只需先支持低多边形仓房、简单人物、木料和一张可改变形状的布面。可用 `BufferGeometry` 从顶点更新表面，用 `Raycaster` 将玩家点击的网格还原为同一块布的对象标识。预览使用临时轮廓，取消即可清除。篷布展开或折回可用少量预设变形表达，无需进行逐帧布料物理模拟。[Three.js 几何体文档](https://threejs.org/docs/pages/BufferGeometry.html) · [Three.js 点选文档](https://threejs.org/docs/pages/Raycaster.html)

只有起草与修改方案会调用模型。游戏经理返回的是引擎可校验的数据，实际执行和渲染均由本地程序完成。模型等待期间玩家仍可检查场景。若等待期间布已被占用、人物已出工或已经入夜，应按当前状态显示失效原因。

## 6. 交付顺序与通过条件

1. **先验证世界与画面一致。** 用固定测试草案分别跑通搭棚和盖货。相同初始快照、相同搭建记录应能重放出相同的网格位置、点选对象和夜间结果。此步验证引擎与渲染，模型尚待验证。
2. **再接入真实模型。** 让玩家分别用自己的话完成 A、B 两局。两局共享资源操作、布面渲染和覆盖判断。检查行动条件是否保留、确认前是否未扣资源、执行后是否只占用一块布。一旦程序需要按“帐篷”或“盖货”关键词调用专用成品脚本，就应记录为样例特例。
3. **做一次资源反例。** 移除篷布或把它预先占用，再提交同一句搭棚指令。预期能说明缺少哪项资源，且不新增布面、床位或劳作消耗。另将篷布缩小到不能覆盖一户，仍可显示实际遮盖面积，但不能按整户入住。
4. **做两项独立的观察。** 让旁观者在隐藏日志与对象名称时看两局画面，指出布去了哪里，并点中实际搭成的物件。再冻结代码和提示词，请没看过示例的试玩者，仅依据场景事实自拟一种用途或使用条件，先写下预期，再操作核对。记录成功和失败的原话、草案及结果。

**判断依据**　A、B 两局通过，说明同一材料能因玩家的指令得到不同的外形和用途。旁观者能看懂，说明三维表现传达了玩法变化。陌生方案也能运行，才为“模型能在已有资源上引入开发者未逐项预写的新玩法”提供初步证据。
